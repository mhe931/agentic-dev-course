Exercise 2.3: Agent Hooks — Programmatic Guardrails

Objective

Use agent hooks to enforce guardrails with code instead of configuration — build a PreToolUse hook that blocks destructive commands, then a PostToolUse hook that auto-formats edited files.

Background

The guardrails you've set up so far come in two tiers: instruction files are soft guidance the model can misinterpret or ignore, and the command allowlist (Exercise 2.1) plus tools restrictions (Exercise 2.2) are configured guardrails the agent works within. Hooks add a third tier: programmatic guardrails — scripts that run at fixed points in the agent lifecycle, every time, regardless of what the model decides.

A hook is a command defined in a JSON file in .github/hooks/. VS Code runs it at lifecycle events such as SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, and Stop. The hook receives event details (like tool_name and tool_input) as JSON on stdin, and its output controls what happens next — a PreToolUse hook can return a permissionDecision of allow, deny, or ask. When several mechanisms overlap, the most restrictive wins: a hook can deny a command even if your allowlist permits it.

A minimal hooks file looks like this:

{
  "version": 1,
  "hooks": {
    "PreToolUse": [
      { "type": "command", "command": "./scripts/guard.sh", "timeout": 15 }
    ]
  }
}

Note that in VS Code the hook itself decides which tools it cares about by inspecting tool_name from stdin (e.g. runTerminalCommand, editFiles). A matcher field exists in the config format for compatibility with other Copilot surfaces, but VS Code ignores matcher values, so hooks run on all tool invocations regardless of the matcher.

Prerequisite: Agent hooks are in Preview — the format and behavior may change, and your organization can disable hooks via policy. Workspace hooks in .github/hooks/ work once the feature is available; the per-agent hooks field in .agent.md additionally requires the chat.useCustomAgentHooks setting. If Chat: Configure Hooks doesn't appear in the Command Palette, check your VS Code version and org policy first.

Warning: Hook scripts run with the same permissions as VS Code, on every event they are registered for. Review any hook script before enabling it — especially ones generated by the agent or copied from the community.

Steps

  1. In Copilot Chat, type /create-hook and describe the guard you want, e.g.:

    Create a PreToolUse hook that inspects terminal commands and denies anything
destructive: rm -rf, git push --force to main, DROP TABLE, or deleting files
outside the workspace. Return permissionDecision "deny" with a short reason.
Everything else should be allowed.

    Alternatively, run Chat: Configure Hooks from the Command Palette and let the agent fill in the generated file.

  2. Glance at what was generated: the JSON entry in .github/hooks/ and the script it points to. Check that the deny logic reads tool_name/tool_input from stdin and that the script is executable. If something looks off, prompt the agent to fix it rather than editing by hand.

  3. Test the block: in Agent mode, ask the agent to do something your hook should stop (e.g., "delete the build folder with rm -rf"). The tool call should be denied and the agent should see your reason.

  4. Test the pass-through: ask for something harmless (e.g., run the test suite). The hook should let it through without friction.

  5. Add a second hook — automation rather than safety this time. Prompt the agent:

    Add a PostToolUse hook that runs our formatter on any file the agent edits.
Use the formatter this project already uses.

    Make an edit via the agent and confirm the file comes back formatted.

  6. Compare tiers while it's fresh: try adding the same destructive command to your allowlist from Exercise 2.1 and watch the hook still deny it — most restrictive wins.

Expected Outcome

Your project has two working hooks: a guard that deterministically blocks destructive commands no matter what the model or allowlist says, and a formatter that keeps agent edits clean without prompting. You can explain the three guardrail tiers — instructions (soft), configuration (allowlist/tools), hooks (programmatic) — and when to reach for each.

Note: Looking ahead — the same hooks concept extends beyond your IDE. The Copilot cloud agent and Copilot CLI use the same .github/hooks/ location and JSON format (that is why the snippet above carries "version": 1, which GitHub surfaces require), but they report tool names differently (e.g. Bash, Edit instead of runTerminalCommand, editFiles), so a guard script needs per-surface tool-name handling before it becomes a team-wide quality gate. Module 09 picks this up when you design your pipeline.
